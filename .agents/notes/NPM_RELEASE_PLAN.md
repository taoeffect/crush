# NPM Release Plan for `@taoeffects/crush`

## Goal

Enable the `taoeffect/crush` fork (corresponding to the `@taoeffects/crush` npm package) to publish
installable Linux and macOS builds without GoReleaser Pro, so users can install the fork with:

```bash
npm install -g @taoeffects/crush
```

The desired distribution model mirrors the official `@charmland/crush` package:
the npm package is a small JavaScript wrapper. It does not contain all binaries.
During `postinstall`, it detects the current platform/architecture, downloads the
matching archive from the GitHub Release for the package version, verifies it,
extracts the `crush` binary, and exposes it through npm's `bin` mechanism.

## Current blockers

1. GitHub Actions are disabled on `taoeffect/crush` repo.
2. Existing release workflows depend on Charm-owned reusable workflows.
3. Existing release workflows target Charm's private runner group:

   ```yaml
   runs-on:
     group: releasers
   ```

4. Existing GoReleaser config uses GoReleaser Pro-only features, including
   `npms:`.
5. Existing release config publishes to Charm-owned channels such as
   `@charmland/crush`, Homebrew, Scoop, NUR, AUR, Docker, Fury, and Winget.
6. The repository currently has no npm package source files; the official npm
   package files are generated by GoReleaser Pro.
7. Existing CI/release branch triggers assume upstream's `main`, while this
   fork's default branch is `taoeffect`.

## User setup required

### 1. Enable GitHub Actions

In GitHub:

1. Open `taoeffect/crush`.
2. Go to **Settings** → **Actions** → **General**.
3. Enable Actions for the repository.
4. Under workflow permissions, allow at least:
   - **Read and write permissions** for `GITHUB_TOKEN`.

The release workflow will need `contents: write` so it can create GitHub Releases
and upload release assets.

### 2. Create or confirm npm scope ownership

To publish `@taoeffects/crush`, the npm account used by CI must be allowed to
publish packages under the `@taoeffects` scope.

User action:

1. Log in to npm.
2. Create or confirm access to the `@taoeffects` organization/scope.
3. Confirm the package name `@taoeffects/crush` is available or controlled by the
   account/org.

### 3. Choose npm authentication method

There are two viable options.

#### Option A: npm trusted publishing

Preferred if the npm account/org supports it. For a new npm package, publish
`@taoeffects/crush` manually once first, then configure trusted publishing for
subsequent releases.

Advantages:

- No long-lived npm token stored in GitHub.
- Uses GitHub OIDC.

User action:

1. Complete the first manual publish of `@taoeffects/crush` using the generated
   npm package from this repository.
2. In npm, configure trusted publishing for package `@taoeffects/crush`.
3. Link it to the GitHub repository `taoeffect/crush`.
4. Restrict publishing to the intended workflow file, for example
   `.github/workflows/release-taoeffect.yml`.
5. Restrict publishing to tag refs matching `v*.*.*` if npm offers that option.

GitHub workflow requirements:

```yaml
permissions:
  contents: write
  id-token: write
```

No `NPM_TOKEN` secret is needed.

#### Option B: npm automation token

Simpler and broadly supported.

User action:

1. In npm, create an automation token with permission to publish
   `@taoeffects/crush`.
2. In GitHub, open `taoeffect/crush`.
3. Go to **Settings** → **Secrets and variables** → **Actions**.
4. Create repository secret:

   ```text
   NPM_TOKEN
   ```

5. Set its value to the npm automation token.

GitHub workflow requirements:

```yaml
permissions:
  contents: write
```

Workflow publish step will use:

```yaml
env:
  NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
```

## Minimal secrets

For the recommended implementation:

| Secret | Required | Why |
|---|---:|---|
| `NPM_TOKEN` | Only if not using trusted publishing | Authenticates `npm publish` |

No custom secret is needed for GitHub Release creation. Use the built-in
`${{ github.token }}` / `${{ secrets.GITHUB_TOKEN }}` with `contents: write`.

No `GORELEASER_KEY` is needed because this plan avoids GoReleaser Pro.

## Repository changes

### 1. Add a fork-specific release workflow

Create a new workflow, for example:

```text
.github/workflows/release-taoeffect.yml
```

Trigger it only on semantic version tags:

```yaml
on:
  push:
    tags:
      - "v*.*.*"
  workflow_dispatch:
```

Use regular GitHub-hosted runners, not Charm's private runner group.

Suggested job structure:

1. `test`
2. `build-release-assets`
3. `publish-github-release`
4. `publish-npm`

The workflow should set explicit permissions:

```yaml
permissions:
  contents: write
  id-token: write # only required for npm trusted publishing
```

If using `NPM_TOKEN` instead of trusted publishing, `id-token: write` can be
omitted.

### 2. Build only the required platforms

Initial target matrix:

| OS | Go `GOOS` | Go `GOARCH` | npm platform key |
|---|---|---|---|
| Linux x64 | `linux` | `amd64` | `linux-x64` |
| Linux arm64 | `linux` | `arm64` | `linux-arm64` |
| macOS Intel | `darwin` | `amd64` | `darwin-x64` |
| macOS Apple Silicon | `darwin` | `arm64` | `darwin-arm64` |

Build flags should match upstream as closely as practical:

```bash
CGO_ENABLED=0 GOEXPERIMENT=greenteagc go build \
  -trimpath \
  -ldflags "-s -w -X github.com/charmbracelet/crush/internal/version.Version=${VERSION}" \
  -o dist/${ARCHIVE_DIR}/crush .
```

Where `VERSION` is the tag without the leading `v`, e.g. `0.67.0`.

Archive naming should be deterministic and easy for the npm installer to derive:

```text
crush_${VERSION}_Linux_x86_64.tar.gz
crush_${VERSION}_Linux_arm64.tar.gz
crush_${VERSION}_Darwin_x86_64.tar.gz
crush_${VERSION}_Darwin_arm64.tar.gz
```

Each archive should wrap files in a directory with the same basename, matching
upstream's pattern:

```text
crush_${VERSION}_Linux_x86_64/crush
crush_${VERSION}_Linux_x86_64/README.md
crush_${VERSION}_Linux_x86_64/LICENSE.md
```

Generate a `checksums.txt` file with SHA-256 sums for all archives:

```bash
sha256sum dist/*.tar.gz > dist/checksums.txt
```

On macOS runners, use `shasum -a 256`; on Linux runners, `sha256sum`. The
simplest path is to create archives/checksums on `ubuntu-latest` using Go cross
compilation for both Linux and macOS.

### 3. Create a GitHub Release

Use the GitHub CLI or an existing action to create/upload release assets.

Example approach:

```bash
gh release create "${TAG}" dist/*.tar.gz dist/checksums.txt \
  --repo "${GITHUB_REPOSITORY}" \
  --title "${TAG}" \
  --generate-notes
```

Environment:

```yaml
env:
  GH_TOKEN: ${{ github.token }}
```

The GitHub Release must exist before publishing npm, because npm `postinstall`
will download archives from that release.

### 4. Add npm package source files

Add a dedicated npm package directory, for example:

```text
npm/
  package.json
  install.js
  run-crush.js
  lib.js
```

The release workflow should copy these files to a temporary package directory,
replace the version, inject archive metadata, and run `npm publish` from that
temporary directory. Avoid publishing directly from the repository root.

Suggested generated npm package structure:

```text
package/
  package.json
  install.js
  run-crush.js
  lib.js
  README.md
  LICENSE.md
```

### 5. npm `package.json`

Template values:

```json
{
  "name": "@taoeffects/crush",
  "type": "module",
  "version": "0.0.0",
  "description": "A terminal-based AI coding assistant forked from Charm Crush.",
  "scripts": {
    "postinstall": "node install.js",
    "run": "node run-crush.js"
  },
  "repository": {
    "type": "git",
    "url": "git+https://github.com/taoeffect/crush.git"
  },
  "license": "FSL-1.1-MIT",
  "bugs": {
    "url": "https://github.com/taoeffect/crush/issues"
  },
  "bin": {
    "crush": "run-crush.js"
  },
  "dependencies": {
    "proxy-agent": "8.0.1",
    "tar": "7.5.13"
  },
  "files": [
    "install.js",
    "run-crush.js",
    "lib.js",
    "README.md",
    "LICENSE.md"
  ]
}
```

`jszip` is not needed while only shipping `.tar.gz` archives. Add it later if
Windows `.zip` support is reintroduced.

### 6. npm installer behavior

`install.js` should:

1. Determine `process.platform` and `process.arch`.
2. Map supported platforms:

   ```text
   linux/x64   -> Linux_x86_64
   linux/arm64 -> Linux_arm64
   darwin/x64  -> Darwin_x86_64
   darwin/arm64 -> Darwin_arm64
   ```

3. Read archive metadata embedded in `package.json`, or construct URLs from
   package version and a hard-coded repo owner/name.
4. Download the archive from:

   ```text
   https://github.com/taoeffect/crush/releases/download/v${VERSION}/${ARCHIVE_NAME}
   ```

5. Verify the SHA-256 digest against embedded metadata.
6. Extract the archive into a package-local directory, for example:

   ```text
   vendor/crush
   ```

7. Ensure the binary is executable on Unix-like systems.

The installer should fail with a clear message for unsupported platforms.

### 7. npm runner behavior

`run-crush.js` should:

1. Resolve the installed binary path, for example:

   ```text
   vendor/crush/crush
   ```

2. Spawn it with `process.argv.slice(2)`.
3. Forward stdio.
4. Exit with the same exit code/signal.

### 8. Metadata generation

The release workflow should generate archive metadata for npm before publishing.

Recommended generated field in `package.json`:

```json
{
  "crush": {
    "repo": "taoeffect/crush",
    "archives": {
      "darwin-arm64": {
        "name": "crush_0.67.0_Darwin_arm64.tar.gz",
        "url": "https://github.com/taoeffect/crush/releases/download/v0.67.0/crush_0.67.0_Darwin_arm64.tar.gz",
        "checksum": {
          "algorithm": "sha256",
          "digest": "..."
        },
        "wrappedIn": "crush_0.67.0_Darwin_arm64",
        "bin": "crush"
      }
    }
  }
}
```

This avoids hard-coding every version into source files.

Implement metadata generation with a small script, for example:

```text
scripts/generate-npm-package.mjs
```

This script should:

1. Read `VERSION` and `TAG` from environment variables or CLI args.
2. Read `dist/checksums.txt`.
3. Copy npm template files into a temporary package directory.
4. Copy `README.md` and `LICENSE.md`.
5. Update `package.json` version.
6. Add archive metadata.
7. Run `npm pack --dry-run` as a sanity check.

### 9. Publish npm package

If using `NPM_TOKEN`:

```yaml
- uses: actions/setup-node@48b55a011bda9f5d6aeb4c2d9c7362e8dae4041e # v6.4.0
  with:
    node-version: "24"
    registry-url: "https://registry.npmjs.org"

- run: npm publish --access public
  working-directory: .release/npm-package
  env:
    NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
```

If using trusted publishing:

```yaml
- uses: actions/setup-node@48b55a011bda9f5d6aeb4c2d9c7362e8dae4041e # v6.4.0
  with:
    node-version: "24"
    registry-url: "https://registry.npmjs.org"

- run: npm publish --access public
  working-directory: .release/npm-package
```

The workflow must have:

```yaml
permissions:
  id-token: write
```

### 10. Keep upstream release workflow disabled or separate

Do not try to reuse `.github/workflows/release.yml` as-is. It is tailored to
Charm's infrastructure and GoReleaser Pro.

Recommended options:

1. Leave upstream workflow present but avoid triggering it in the fork.
2. Rename/disable it in the fork.
3. Add a new fork-specific release workflow and document that releases should use
   that workflow.

If keeping the upstream workflow file, ensure tags do not trigger both workflows
or make the upstream workflow opt out for this fork.

## Suggested implementation order

### Phase 1: CI and artifact builds

1. Enable GitHub Actions in repo settings.
2. Add `.github/workflows/release-taoeffect.yml`.
3. Build four archives on `ubuntu-latest` by cross-compiling Go.
4. Generate `checksums.txt`.
5. Create a GitHub Release from a test tag.
6. Verify release assets manually by downloading and running the binary.

Success criteria:

- A pushed tag creates a GitHub Release.
- The release includes Linux/macOS x64/arm64 archives.
- The release includes `checksums.txt`.
- Extracted binaries run and report the expected version.

### Phase 2: npm package generation

1. Add npm template files under `npm/`.
2. Add `scripts/generate-npm-package.mjs`.
3. Generate package metadata from `dist/checksums.txt`.
4. Run `npm pack --dry-run` in CI.
5. Locally test the packed package against a draft/test release.

Success criteria:

- `npm pack --dry-run` shows only expected package files.
- `package.json` contains correct version and archive metadata.
- `install.js` downloads and verifies the correct platform archive.

### Phase 3: npm publish

1. For the first npm release, manually publish the generated package with
   `npm publish --access public` from the package output directory.
2. Configure npm trusted publishing for subsequent releases, or configure
   `NPM_TOKEN` if trusted publishing is unavailable.
3. Add npm publish step after GitHub Release creation.
4. Push a new tag.
5. Confirm npm package published as `@taoeffects/crush@VERSION`.
6. Test:

   ```bash
   npm install -g @taoeffects/crush
   crush --version
   ```

Success criteria:

- `npm install -g @taoeffects/crush` installs successfully on Linux and macOS.
- Running `crush` launches the forked binary.
- The installed version matches the tag.

## Release process after implementation

1. Ensure branch `taoeffect` is ready.
2. Create and push a new tag:

   ```bash
   git tag vX.Y.Z
   git push taoeffect vX.Y.Z
   ```

3. GitHub Actions builds archives.
4. GitHub Actions creates the GitHub Release.
5. GitHub Actions publishes `@taoeffects/crush@X.Y.Z` to npm.
6. Users install with:

   ```bash
   npm install -g @taoeffects/crush
   ```

## Notes and tradeoffs

- macOS signing/notarization is not included in the minimal plan. Unsigned
  binaries may trigger macOS Gatekeeper warnings depending on how users run them.
  Adding signing later requires Apple Developer credentials and additional
  secrets.
- Windows support is intentionally omitted from this plan. Add `.zip` support
  and `win32-*` metadata later if desired.
- Linux package managers, Homebrew, Scoop, NUR, AUR, Docker, Fury, and Winget are
  intentionally omitted.
- This plan avoids GoReleaser Pro entirely. Free GoReleaser could still be used
  for archives if desired, but plain shell/Go commands are enough for the
  initial Linux/macOS/npm distribution.
- Use a test package or prerelease tag first if possible, because npm versions
  are immutable once published.
